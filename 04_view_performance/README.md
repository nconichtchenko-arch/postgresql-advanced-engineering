# Анализ производительности: VIEW vs Table (Нагрузочное тестирование)

## 🎯 Задача
Проверить распространенный миф: «Запрос к виртуальной таблице (VIEW) работает медленнее, чем прямой запрос к оригинальной таблице».

## 🛠 Методология
Тестирование проводилось в два этапа с использованием утилиты `pgbench`:
1.  **Низкая нагрузка:** 10 клиентов, 1000 транзакций, таблица на 1 млн строк.
2.  **Высокая нагрузка:** 90 клиентов, 10 000 транзакций, таблица на 10 млн строк.

Для каждой нагрузки сравнивались два запроса:
*   `SELECT * FROM student WHERE id = 1;` (к таблице)
*   `SELECT * FROM v_student WHERE id = 1;` (к VIEW)

## 📊 Результаты

| Параметр | Низкая нагрузка (Таблица) | Низкая нагрузка (VIEW) | Высокая нагрузка (Таблица) | Высокая нагрузка (VIEW) |
| :--- | :--- | :--- | :--- | :--- |
| **Latency** | 0.707 мс | 0.744 мс | 7.135 мс | 6.930 мс |
| **TPS** | 14149.29 | 13434.54 | 12614.68 | 12986.43 |

## 💡 Вывод
Миф не подтвердился в полной мере:
1.  При **низкой нагрузке** VIEW немного медленнее (разница ~5%), что связано с оверхедом на разворачивание плана.
2.  При **высокой нагрузке** VIEW показал себя **быстрее** (TPS выше на 3%), благодаря кэшированию планов запросов в PostgreSQL.
3.  `EXPLAIN ANALYZE` подтвердил, что оба запроса используют `Index Scan` по первичному ключу, поэтому разница в производительности минимальна.
